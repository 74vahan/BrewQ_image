# Правила работы (VibeCode)

## 1. Языки UI
Если в задаче нет уточнения, интерфейс (UI) всегда делается на трёх языках: английский (en), русский (ru), армянский (hy). Переводы хранятся в отдельных файлах локализации (i18n), а не захардкожены в разметке.

## 2. Язык общения
Независимо от того, на каком языке написан промпт, ассистент всегда общается на русском.

## 3. Папка memory в каждом проекте
В каждом проекте рядом с кодом создаётся папка `memory/`. Про каждый аспект сайта/проекта — отдельный `.md` файл. Каждый файл имеет индекс (числовой префикс), например:

```
memory/
  INDEX.md          — оглавление: список всех файлов с кратким описанием
  01-architecture.md
  02-database.md
  03-api.md
  04-ui.md
  05-deploy.md
```

## 4. Работа с памятью
Перед началом любой работы над проектом — прочитать его `memory/`. После любых изменений — обновить соответствующие файлы памяти и `INDEX.md`.

## 5. Проверка на кириллицу
После каждой работы проверять код на случайные кириллические символы (опечатки, похожие буквы: с/c, а/a, е/e, о/o и т.д.). Кириллица допустима только в файлах локализации (ru-переводы), комментариях и документации.

## 6. Термины
Технические термины можно оставлять на английском.

## 7. Структура кода
Проект НИКОГДА не состоит из больших монолитных кусков кода. Код всегда разделён на логические части (модули), готов к масштабированию (scale) и лёгок для поддержки человеком. Ориентир: один файл — одна ответственность, файлы не разрастаются до сотен строк без причины.

## 8. Сомнения
Если есть какие-то сомнения или неоднозначность в задаче — спросить пользователя, а не угадывать.

## 9. Секреты вне кода
Никаких токенов, паролей, API-ключей в коде и в git. Все секреты — только в `.env` файлах, а `.env` всегда добавлен в `.gitignore`. В репозитории хранится только `.env.example` с пустыми значениями.

## 10. Проверка после изменений
После каждого изменения запустить/протестировать проект и убедиться, что всё работает, прежде чем сообщать «готово». Если проверить невозможно — честно сказать, что не проверено.

## 11. README в каждом проекте
В каждом проекте держать актуальный `README.md`: что это за проект, как запустить локально, как задеплоить. При изменениях, влияющих на запуск или деплой, — обновлять README.

## 12. Проверка skills-lock.json
Перед началом любой работы заглянуть в `skills-lock.json` (в корне VibeCode) — это список подключённых agent-скиллов. Если среди них есть навык, релевантный текущей задаче, — использовать его. Сами скиллы лежат в `.agents/skills/<name>/SKILL.md`.

## 13. Папка .claude в каждом проекте
В каждом проекте должна быть папка `.claude` — точная копия корневой `.claude` из VibeCode (с теми же файлами, включая `commands/` со всеми командами, например `Push.md` и `QA.md`). При создании нового проекта — сразу скопировать туда корневую `.claude`. Если в корневой `.claude` появляются новые файлы/команды или меняются существующие — синхронизировать эти изменения во все проекты.

## 14. Базовый набор сабагентов в каждом проекте
В каждом новом проекте должна быть папка `.claude/agents/` с базовым набором сабагентов Claude Code. Базовый набор хранится в корневой `.claude/agents/` VibeCode и при создании проекта копируется вместе с папкой `.claude` (см. правило №13).

Базовый набор (source: VoltAgent/awesome-claude-code-subagents):

**Фронтенд / фундамент:**
- `nextjs-developer` — Next.js (App Router, SSR/SSG/ISR, Server Components)
- `typescript-pro` — TypeScript
- `react-specialist` — React (компоненты, хуки, паттерны)
- `frontend-developer` / `fullstack-developer` — связка фронт↔бэк, архитектура
- `ui-designer` — визуал и UX
- `accessibility-tester` — a11y
- `code-reviewer` — качество и структура кода

**Бэкенд:**
- `backend-developer` — серверная логика, масштабируемые API
- `api-designer` — проектирование REST/GraphQL
- `postgres-pro` — схема БД, индексы, запросы
- `database-optimizer` — производительность запросов
- `security-auditor` — уязвимости, защита персональных данных

**Инфраструктура / деплой:**
- `devops-engineer` — CI/CD
- `deployment-engineer` — автоматизация деплоя
- `docker-expert` — контейнеризация
- `terraform-engineer` — IaC (GCP)

Если базовый набор в корневой `.claude/agents/` меняется (добавлены/обновлены агенты) — синхронизировать во все проекты (аналогично правилу №13).

## Git
`git push` выполняется только по явной просьбе пользователя (никогда автоматически).
